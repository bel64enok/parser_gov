# PRD — Вкладка «ИИ-анализ»: управление стадией 2 (ReAct-агент извлечения данных)

Статус: черновик к реализации · Автор: пресейл-команда · Дата: 2026-06-09

## 1. Контекст и проблема

Стадия 2 пайплайна (`analyzer.py` + `ai.py`) сейчас:
- склеивает текст всех документов тендера, **грубо обрезает до 30 000 символов** и делает
  **один** запрос к шлюзу RMR (`gpt-oss-120b`, OpenAI-совместимый) → мягкая выжимка
  (`summary / requirements / risks / suggested_domain / confidence / deadline_note`);
- не выбирает документы, не ищет факты, не итерирует;
- **никакого следа рассуждений** не сохраняется — этап «спрятан», его логика неочевидна,
  понять «почему агент решил так» нельзя ни во время прогона, ни постфактум (cron ночью).

**Боль:** этап непрозрачен и неуправляем. Нельзя руками перезапустить, посмотреть, что
именно ИИ прочитал и откуда взял вывод. Обрезка в 30k теряет ровно те договорные цифры
(обеспечение, объёмы, штрафы), которые нужны пресейлу.

## 2. Цели и не-цели

**Цели**
- Переделать стадию 2 на **ReAct-агента** (петля «рассуждение → инструмент → наблюдение»),
  который **навигирует по комплекту документов** инструментами вместо обрезки в один промпт.
- Агент извлекает **структурированную карточку требований** (раздел 6) с цитатами-источниками.
- **Отдельная техническая вкладка** для управления и разбора этого этапа — прозрачный
  пошаговый трейс работы агента по каждому тендеру.

**Не-цели (в этой итерации)**
- Не делаем редизайн менеджерской вкладки «Тендеры» — туда лишь **минимально прокидываем**
  структурированную карточку (полноценный UX-редизайн — отдельная задача).
- Не выкидываем правила (`analyze_tender`): детерминированный скоринг/очередь/чеклист
  остаются слоем под агентом и фолбэком.
- Не добавляем агенту доступ в интернет — работает только по скачанному комплекту (офлайн,
  детерминированно).
- Не вводим новых тяжёлых зависимостей — петля пишется руками на уже имеющемся `openai` SDK.

## 3. Пользователи

| Роль | Где работает | Что получает |
|---|---|---|
| **Технический оператор / разработчик** | новая вкладка «ИИ-анализ» | запуск анализа, живой прогресс, полный ReAct-трейс, разбор «почему так» |
| **Пресейл-менеджер** | существующая вкладка «Тендеры» | структурированная карточка требований в карточке тендера (минимально) |

Эта вкладка — **техническая**, по духу повторяет вкладку «Сбор документов» (Crawler):
ось «по прогонам», master-detail, технический язык.

## 4. Пользовательские сценарии (что я вижу)

1. **Запускаю анализ.** Вижу статус шлюза (подключён/нет), счётчики очереди
   (`в очереди N · готово · ошибок`), жму «Запустить анализ» — батч прогоняет все тендеры
   в статусе `fetched`. Вижу живой прогресс: `тендер 3/12` + текущий шаг человеческим языком
   («читает `ТЗ.docx`», «ищет „обеспечение заявки"»).
2. **Смотрю список прогонов** (master) — статус, тип (cron/ручной), сколько тендеров,
   шагов, длительность, когда начат.
3. **Открываю прогон** (detail) — тендеры этого прогона: №, название, статус
   (в очереди/анализируется/готов/готов с лимитом/ошибка), домен, уверенность, число шагов.
4. **Открываю тендер** (drawer, табы):
   - **Трейс** (дефолт) — пошаговый ReAct-лог: `шаг N · мысль → инструмент(аргументы) →
     наблюдение(сниппет)`, до финального `submit_card`; кнопка **«Переанализировать»**;
   - **Карточка** — структурированные требования (раздел 6) с цитатами-источниками;
   - **Документы** — какие файлы агент видел (имя, тип, размер, прочитан ли).
5. **Переанализирую** один тендер новым прогоном — старый трейс остаётся в истории.
6. **Ночной cron** отработал — его прогон виден в списке так же, как ручной; трейс по каждому
   тендеру сохранён и доступен (этап больше не «спрятан»).

## 5. ReAct-агент

### 5.1 Объектив
Собрать структурированную карточку требований (раздел 6), привязав каждый факт к
документу-источнику. Не выдумывать: пустое поле → «не найдено в документации».

### 5.2 Инструменты (tools)
| Инструмент | Назначение |
|---|---|
| `list_documents()` | список файлов тендера (имя, тип, размер) — что вообще есть |
| `read_document(doc_id, chunk)` | читает один документ по кускам (не весь комплект сразу) |
| `search_documents(query)` | поиск подстроки/ключевых слов по всем документам — где лежит факт |
| `lookup_dictionary()` | словарь доменов/продуктов из `rules.py` (`DOMAIN_TRIGGERS`, `PRODUCT_CATALOG`) — домен согласован с правилами |
| `submit_card(json)` | финализация: заполненная структура; петля завершается |

Без `web_fetch` и любого сетевого доступа за пределы шлюза.

### 5.3 Реализация петли
- **Руками на `openai` SDK** (без Claude Agent SDK / LangGraph / openai-agents).
- На старте реализации **проверяется на шлюзе**, поддерживает ли он нативный function-calling
  для `gpt-oss-120b`:
  - **поддерживает** → нативные OpenAI tools;
  - **нет** → фолбэк: текстовый ReAct-протокол через `response_format={"type":"json_object"}`
    (модель возвращает `{"thought","action","action_input"}`, петлю парсим сами).
  - Снаружи (трейс, карточка, UI) поведение одинаково.

### 5.4 Предохранители
- **Лимит шагов** на тендер: 12–15 вызовов инструментов. Упёрлись → принудительный
  `submit_card` собранным (частичная карточка) + флаг «достигнут лимит шагов».
  Это статус **`done` с пометкой**, не `error`.
- **Таймаут** на тендер ~120 c.
- **Последовательно**, один воркер-тред, **общий single-run guard** с Crawler
  (`db.active_run()`): сбор и анализ взаимоисключающи.
- **Деградация**:
  - шлюз недоступен на старте батча → агент пропускается, тендеры размечаются правилами
    (`model="rules-only"`, как сейчас);
  - падение/таймаут агента на одном тендере → сохраняем частичный трейс, тендер → `error`,
    **батч продолжается** (изоляция по тендеру).
- Тендер без скачанных документов → агент работает по тексту карточки
  (`rules.document_text_for_tender`).

## 6. Структурированная карточка (выход агента)

Дополняет детерминированный чеклист правил (домен / способ закупки / сроки подачи / ОКПД2 /
НМЦК / score уже считаются в `rules.analyze_tender`), извлекая факты из **тела документов**.

| Секция | Поля |
|---|---|
| **Предмет** | предмет закупки; объём/количество (напр. «5000 SIM», «120 каналов»); территория оказания |
| **Коммерческие условия** | обеспечение заявки (сумма/%); обеспечение контракта (сумма/%); условия и график оплаты; штрафы/неустойки |
| **Сроки** | период оказания услуг; срок исполнения контракта; ключевые даты (подача / рассмотрение) |
| **Требования к участнику** (go/no-go) | лицензии связи; СРО/допуски; опыт/референсы; прочие квалификационные — каждый с пометкой «есть в документации: да/нет» |
| **Технические требования** | SLA; скорости/ёмкость; покрытие/география сети; прочие тех. условия |
| **Итого** | домен (из словаря); summary (2–3 предложения); риски; общая уверенность (высокая/средняя/низкая) |

**Формат факта:** `{ value, source: { filename, quote }, step_ref }` — значение + файл-источник +
точная цитата + ссылка на шаг трейса. Пусто → `value = "не найдено в документации"`.
**Нормализация:** значение хранится как в документе (строкой, для цитаты) + по возможности
нормализованное число/дата рядом. **Уверенность** — общая по карточке + флаг «не найдено»
на полях (отдельное число на каждый факт не вводим).

## 7. Данные

- **Новая таблица `agent_runs`** — одна строка на *попытку* анализа тендера (история всех
  попыток сохраняется):
  `id, tender_number, pipeline_run_id, status(running|done|error), model, started_at,
  finished_at, duration_sec, step_count, tool_calls, tokens, error, card_json, steps_json`.
  Полный трейс — JSON-блоб `steps_json` (в стиле проекта; отдельной таблицы шагов нет).
- **Расширение `analysis`** одним полем `agent_card_json` — «последняя карточка». Её читает
  стадия 3 (`db.query_tenders`), поэтому карточка автоматически появляется и во вкладке
  «Тендеры» (минимальный проброс для менеджера).
- Миграция — через существующий идемпотентный `db._migrate()` (ALTER + новая таблица).

## 8. Триггеры и связь с пайплайном

- **Кнопка «Запустить анализ»** — батч по тендерам `fetched`, фоновый воркер, single-run guard.
- **«Переанализировать»** один тендер (в т.ч. уже `analyzed`) — новый прогон/попытка.
- **Cron** остаётся (полный пайплайн раз в час), стадия анализа использует **того же агента**,
  что и ручной запуск — единый код в `analyzer.py`, не две реализации.
- Правила (`analyze_tender`) — детерминированный слой под агентом и фолбэк.

## 9. API (новые эндпойнты, по образцу crawler)

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/api/analysis` | обзор: статус шлюза, очередь, активный прогон, список прогонов анализа |
| `GET` | `/api/analysis/run?id=` | деталь прогона: тендеры со сводкой (статус, домен, шаги) |
| `GET` | `/api/analysis/tender?number=` | трейс + карточка + документы одного тендера |
| `POST` | `/api/analysis/start` | старт батча (`{}` → все `fetched`); 409 если уже идёт прогон |
| `POST` | `/api/analysis/reanalyze` | `{number}` — переанализ одного тендера |

Страница: `/analysis.html` (+ редирект `/analysis`), `static/analysis.js`, переиспользуем
`styles.css` и паттерны drawer/таблиц из crawler. Навигация: добавить пункт **«ИИ-анализ»**
в `nav` всех страниц.

## 10. Метрики/наблюдаемость
- Токены и длительность показываем на этой технической вкладке (прогон/тендер), **не** на
  карточке менеджера.
- Прогресс: idle-polling ~20 c, active ~2 c (как crawler).

## 11. Edge-cases
- Старый тендер без документов → анализ по тексту карточки.
- Прогон оборвался (`stalled`) → виден как в crawler (старше `STALE_RUN_MIN`).
- Невалидный JSON от модели в финале → ретрай финализации в пределах лимита шагов; иначе
  частичная карточка / `error`.
- Двойной клик «Запустить»/«Переанализировать» → защита `busy` + single-run guard (409).

## 12. Риски / открытые вопросы
- **Главный риск:** поддерживает ли RMR-шлюз нативный function-calling для `gpt-oss-120b`.
  Митигируется проверкой на старте + фолбэком на JSON-action протокол (раздел 5.3).
- Качество извлечения цитат зависит от качества `extract.extract_text_from_file` (pdf-сканы
  без текстового слоя дадут пустой текст — поле «не найдено»).
